# VAL-001 — MD-001 Deterministic Normalization Validator Specification

## 1. Purpose and Architecture

`VAL-001` specifies the automated refereeing engine responsible for evaluating candidate documents produced by the normalization workflow. Acting as the sole authority on file acceptance, the validator operates independently of any upstream transformer (`Mistral`), enforcing the **Authorized Transformation Invariant** defined in `MD-001 v1.0`.

```text
Source Document (S) ──┐
                      ├──► [VAL-001 Engine] ──► { COMPLIANT | NORMALIZED | QUARANTINE }
Candidate Document (C)┘
```

## 2. Inputs and Outputs

### 2.1. Inputs

1. **Source Document ($S$):** The raw Markdown file prior to transformation (may contain legacy formatting).
2. **Candidate Document ($C$):** The proposed output file generated by the transformer.
3. **Normative Standard (`MD-001 v1.0`):** The immutable ruleset governing permitted structures and transformations.

### 2.2. Outputs

Every execution yields a structured validation result containing:

- **Outcome Flag:** Exactly one of `COMPLIANT`, `NORMALIZED`, or `QUARANTINE`.
- **Unified Diff ($D$):** A strict byte-level unified diff comparing $S$ and $C$.
- **Classification Log:** An itemized breakdown mapping every structural or content delta to a permitted transformation class or an unauthorized violation.
- **Audit Metadata:** Execution timestamp, validator version, document identifiers, and explicit error codes (if quarantined).

## 3. Validation Pipeline & Execution Stages

The validator executes sequentially through five distinct validation gates. Failure at any gate short-circuits the pipeline and routes the candidate directly to `QUARANTINE`.

```text
[Stage 1: Frontmatter & Legacy-Tolerant Schema Parse]
                 │
                 ▼
[Stage 2: Structural Integrity Check (H1/Nesting)]
                 │
                 ▼
[Stage 3: Protected Content Invariance Check]
                 │
                 ▼
[Stage 4: Delta Classification Engine]
                 │
                 ▼
[Stage 5: Final Outcome Assignment]
```

### 3.1. Stage 1: Frontmatter & Schema Parse

- **Source Parse:** Parse $S$ using a legacy-tolerant read-only schema. Recognized legacy metadata-key forms MAY be accepted solely to establish the source baseline. Failure to parse the source sufficiently to establish protected metadata values results in `QUARANTINE`.
- **Candidate Parse:** $C$ MUST satisfy the complete `MD-001 v1.0` frontmatter specification, including required snake_case keys and H1 spacing requirements. Legacy tolerance MUST NOT be applied when determining candidate compliance.

### 3.2. Stage 2: Structural Integrity Check

- Scans the document Abstract Syntax Tree (AST) to confirm exactly one H1 heading (`#`) exists immediately following the frontmatter blank line.
- Validates that all subsequent headings (H2 through H6) adhere strictly to sequential nesting (no skipped levels, e.g., H2 to H4).

### 3.3. Stage 3: Protected Content Invariance Check

- Extracts protected elements from $S$ and $C$ into ordered typed sequences, including fenced code blocks, inline code, table contents, URLs, citation keys, and YAML values.
- Each corresponding protected element MUST retain identical content and relative ordering ($\text{ELEMENT}_{[n]} \text{ of } S == \text{ELEMENT}_{[n]} \text{ of } C$).
- Permitted structural transformations MAY alter byte offsets but MUST NOT alter protected element values, contents, cardinality, or sequence.

### 3.4. Stage 4: Delta Classification Engine

Maps all remaining byte-level and structural deltas outside protected blocks exclusively to the transformation classes permitted by `MD-001`:

- **Heading Syntax Injection:** Addition of `#` through `######` markers.
- **Visual Styling Removal:** Removal of `**`, `*`, or `_` strictly from converted heading lines.
- **Whitespace Normalization:** Trimming trailing whitespace, harmonizing line endings, and normalizing blank lines strictly outside code blocks.
- **Metadata Key Standardization:** Permitted migration of legacy spaced keys to snake_case keys (`document_id`, etc.).

If *any* delta falls outside these permitted classes (e.g., modified prose wording or altered punctuation in sentences), the validator MUST trigger immediate `QUARANTINE`.

### 3.5. Stage 5: Final Outcome Assignment

- If $S$ is identical to $C$ and satisfies `MD-001`: Output **`PASS — COMPLIANT`**.
- If $S \neq C$, all deltas are verified as permitted transformations, and $C$ satisfies `MD-001`: Output **`PASS — NORMALIZED`**.
- If any check fails: Output **`FAIL — QUARANTINE`** with the corresponding error code.

## 4. Error Codes & Quarantine Reasons

When a candidate is quarantined, the validator logs one of the following deterministic error codes:

| Error Code | Category | Description |
| --- | --- | --- |
| `ERR_FM_SYNTAX` | Frontmatter | Malformed YAML, missing required keys, or incorrect spacing in candidate. |
| `ERR_H1_VIOLATION` | Structure | Zero or multiple H1 headings, or incorrect placement relative to frontmatter. |
| `ERR_HEADING_NEST` | Structure | Skipped heading levels (e.g., H2 followed directly by H4). |
| `ERR_PROTECTED_CONTENT` | Content | Modification, reordering, or cardinality mismatch detected inside code blocks, tables, inline code, citations, or YAML values. |
| `ERR_PROSE_MUTATION` | Content | Alteration, addition, deletion, or rewriting of running prose or sentence punctuation. |
| `ERR_UNAUTHORIZED_DELTA` | Transformation | Structural change that does not map to any permitted transformation class in `MD-001 §3.2`. |

## 5. Commissioning Test Matrix (Adversarial Validation Harness)

Before connecting any AI transformer, the validation engine must be tested against a local test harness containing known-good, legacy-tolerant, and deliberately malicious or broken test cases.

| Test ID | Target Type | Description | Expected Outcome |
| --- | --- | --- | --- |
| `TC-VAL-001` | Positive Control | Pristine document already fully compliant with `MD-001`. | `PASS — COMPLIANT` |
| `TC-VAL-002` | Valid Normalization | Document with unformatted bold headers correctly converted to H2 tags; prose untouched. | `PASS — NORMALIZED` |
| `TC-VAL-003` | Adversarial Prose | Transformer slightly rewrites a sentence ("functioning correctly" $\rightarrow$ "functions properly"). | `FAIL — QUARANTINE` (`ERR_PROSE_MUTATION`) |
| `TC-VAL-004` | Code Block Tampering | Transformer strips trailing whitespace or reformats code inside a fenced code block. | `FAIL — QUARANTINE` (`ERR_PROTECTED_CONTENT`) |
| `TC-VAL-005` | Hierarchy Violation | Transformer introduces an H4 heading immediately following an H2 heading. | `FAIL — QUARANTINE` (`ERR_HEADING_NEST`) |
| `TC-VAL-006` | Metadata Sabotage | Transformer alters a version string value or metadata key value. | `FAIL — QUARANTINE` (`ERR_PROTECTED_CONTENT`) |
| `TC-VAL-007` | Phantom Heading | Transformer converts a regular sentence ending in a period into an H3 heading. | `FAIL — QUARANTINE` (`ERR_UNAUTHORIZED_DELTA`) |
| `TC-VAL-008` | Legacy Metadata Migration | Source contains recognized legacy spaced metadata keys; candidate converts only those keys to MD-001 snake_case equivalents while preserving every value. | `PASS — NORMALIZED` |
